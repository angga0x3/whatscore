# Pairing findings

Device-pairing payloads of the multi-device flow. Extracted from read-only
reference study of whatsmeow `pair.go` and from one live pairing attempt that
reached a scannable QR on 2026-11-15. No successful pairing is recorded, so
findings that only the server could confirm stay **Probable**.

The live attempt produced a real result: the phone refused the link, and reading
the code it was given found two defects (PF-072, PF-074) that reading the
reference alone would not have surfaced as *our* bugs.

## PF-015: QR payload format

| Field | Value |
|-------|-------|
| **ID** | PF-015 |
| **Title** | A pairing QR encodes `https://wa.me/settings/linked_devices#<ref>,<noisePub>,<identityPub>,<advSecret>,<clientType>` with base64 (standard, padded) 32-byte keys |
| **Layer** | pairing |
| **Source** | inferred — reference study |
| **Observed date** | 2026-11-15 |
| **Confidence** | Probable |
| **Status** | Verified-by-test |
| **Proving test** | `protocol/pairing` (golden QR, round-trip) |
| **Related findings** | PF-004 (Noise static key), PF-016 (planned) |
| **Notes** | whatsmeow `makeQRData(ref, clientType)`: `fmt.Sprintf("https://wa.me/settings/linked_devices#%s,%s,%s,%s,%s", ref, base64(noisePub), base64(identityPub), base64(advSecret), clientType)`. `ref` is the raw content of a `<ref>` child in the server's `<pair-device>` node (typically ASCII). `clientType` is an opaque enum value; it may be empty when unknown. QR rendering is a caller concern. |

## PF-016: pair-device and pair-success stanzas

| Field | Value |
|-------|-------|
| **ID** | PF-016 |
| **Title** | The server sends `<iq><pair-device><ref>…</ref></pair-device></iq>`; the client acks with an iq result, and pairing completes with `<iq><pair-success>` carrying `device@jid`, `device@lid`, `biz@name`, `platform@name`, `client-props` bytes, and `device-identity` bytes |
| **Layer** | pairing |
| **Source** | inferred — reference study |
| **Observed date** | 2026-11-15 |
| **Confidence** | Probable |
| **Status** | Verified-by-test |
| **Proving test** | `protocol/pairing` (stanza table, binary round-trip) |
| **Related findings** | PF-015 |
| **Notes** | whatsmeow `handlePairDevice` acks with `iq{to: from, id, type: result}` and skips non-`ref` children; `handlePairSuccess` reads the iq `id`, the `pair-success` child, and its `device` (`jid`, `lid`), `biz` (`name`), `platform` (`name`), `client-props`, and `device-identity` children. `device-identity` is an `ADVSignedDeviceIdentityHMAC` protobuf: HMAC-SHA256 over `details` with the adv secret, then account/device XEdDSA signatures. WhatsCore currently returns those bytes opaque; verification and credential provisioning are pending. |

## PF-017: Device-identity authentication

| Field | Value |
|-------|-------|
| **ID** | PF-017 |
| **Title** | `pair-success.device-identity` is an `ADVSignedDeviceIdentityHMAC`: HMAC-SHA256 over `details` with the adv secret, then an account XEdDSA signature over `prefix ‖ details ‖ identityPub` |
| **Layer** | pairing |
| **Source** | inferred — reference study |
| **Observed date** | 2026-11-15 |
| **Confidence** | Probable |
| **Status** | Verified-by-test |
| **Proving test** | `protocol/pairing` (identity table: E2EE, hosted, 12 negatives) |
| **Related findings** | PF-016 |
| **Notes** | Proto field numbers: `ADVSignedDeviceIdentityHMAC{details=1, HMAC=2, accountType=3}`, `ADVSignedDeviceIdentity{details=1, accountSignatureKey=2, accountSignature=3, deviceSignature=4}`, `ADVDeviceIdentity{rawID=1, timestamp=2, keyIndex=3, accountType=4, deviceType=5}`. HMAC message is `details`, or `0x06 0x05 ‖ details` for `HOSTED`; account signature prefix is `0x06 0x00` (E2EE) or `0x06 0x05` (HOSTED), with the 32-byte `accountSignatureKey` and 64-byte signature. The device signature (prefix `0x06 0x01`, over `details ‖ identityPub ‖ accountSignatureKey`) is generated by us and is not verified by the server; generation and credential provisioning are pending. |

## PF-069: The live pairing exchange decodes with twelve tokens

| Field | Value |
|-------|-------|
| **ID** | PF-069 |
| **Title** | The `pair-device` stanza and the subsequent keepalive decode exactly with ten single-byte tokens and two dictionary-1 tokens; the acknowledge is accepted and the server keeps the socket open by pinging `<iq xmlns="urn:xmpp:ping" type="get">` roughly every 30 s |
| **Layer** | pairing |
| **Source** | direct observation of own session |
| **Observed date** | 2026-11-15 |
| **Confidence** | Confirmed |
| **Status** | Verified-by-test |
| **Proving test** | `deployments/tokendict` live run: pair-device decoded to 6 refs, ack sent, two pings decoded and answered |
| **Related findings** | PF-016, PF-068, PF-070 |
| **Notes** | Full decode: `<iq from="@s.whatsapp.net" type="set" id xmlns="md"><pair-device><ref>×6</ref></pair-device></iq>`, then `<iq from type="get" t xmlns="urn:xmpp:ping">`. Answering the ping with an `iq result` carrying the same id keeps the connection alive; ignoring it produces the 1006 close that earlier runs read as "the acknowledgement was rejected". A first mapping placed `t` at index 22 and `xmlns` at 26 and left 41 unknown; the keepalive decode contradicted it, and the corrected ordering (`22=xmlns`, `26=t`, `41=get`, `43=urn:xmpp:ping`) now matches an independent byte walk. That correction is the reason this finding is worth trusting: the wrong table decoded without error. |

## PF-070: Keepalive, not rejection

| Field | Value |
|-------|-------|
| **ID** | PF-070 |
| **Title** | An unpaired session that acknowledges `pair-device` is kept alive by `<iq xmlns="urn:xmpp:ping" type="get" t>`; a client that does not answer is disconnected about 30 s later with a 1006 close |
| **Layer** | transport |
| **Source** | direct observation of own session |
| **Observed date** | 2026-11-15 |
| **Confidence** | Confirmed |
| **Status** | Verified-by-test |
| **Proving test** | `deployments/tokendict` live run: two pings answered, socket stayed open across both |
| **Related findings** | PF-069 |
| **Notes** | Pings arrived with `t` values 31 s apart, consistent with the reference client's keepalive interval. Answering requires an `iq` with `type="result"`, `to="s.whatsapp.net"`, and the ping's `id`; the amount of the reply did not matter to the server within the window observed. This also means a client that stops reading looks like a rejected pair to any observer who only watches for closes. |

---

Status: the pairing exchange works end to end against the live server up to and
including a **verified `pair-success`** (PF-075).

The history here matters more than the status line. A first phone attempt was
refused; auditing it found three defects — a zero-filled signed-prekey signature
(PF-072), all six QR codes printed at once although only one is valid at a time
(PF-074), and no `pair-device-sign` confirmation (PF-073). After those fixes a
second scan **succeeded at the server**: a real `pair-success` arrived and its
account identity verified against our own adv secret and identity key.

The probe still could not use it, for a different reason: its partial token table
could not decode the stanza (PF-075), and the unconfirmed link was then aborted
by the server (PF-076). The tokens are now known and recorded, and the fixture
that builds a server-shaped container is covered by a test.

No message has been sent, no session has been established, and no credential
file has been written from a live run. Those remain untested.

## PF-071: qr-client-type derives from the reported platform

| Field | Value |
|-------|-------|
| **ID** | PF-071 |
| **Title** | A QR login reports a concrete browser platform in `DeviceProps.platformType`; the QR `clientType` field is derived from it, and `1` is Chrome |
| **Layer** | pairing |
| **Source** | reference study of whatsmeow `pair.go`, `pair-code.go`, `store/clientpayload.go` |
| **Observed date** | 2026-11-15 |
| **Confidence** | Probable |
| **Status** | Verified-by-test |
| **Proving test** | `cmd/whatscore-probe` (`TestPairingPayloadReportsAChromePlatform`) |
| **Related findings** | PF-015, PF-024 |
| **Notes** | `getQRClientType` maps `DeviceProps.platformType` to `PairClientChrome = "1"`, `Edge = "2"`, `Firefox = "3"`, … The fallback for a plain web client with no platform set is `PairClientOtherWebClient = "9"`, not Chrome. ## PF-072: The registration payload must carry a real signed prekey

| Field | Value |
|-------|-------|
| **ID** | PF-072 |
| **Title** | `eSkeySig` must be an XEdDSA signature by `eIdent` over `0x05 ‖ signedPreKey`; a zero-filled 64-byte signature passes local length checks and is still unusable |
| **Layer** | auth |
| **Source** | reference study of whatsmeow `store.getRegistrationPayload`, plus a phone's own failure report |
| **Observed date** | 2026-11-15 |
| **Confidence** | Confirmed by construction; the server-side rejection is inferred |
| **Status** | Verified-by-test |
| **Proving test** | `cmd/whatscore-probe` (`TestPairingPayloadSignsThePreKey`), `protocol/signal` (`XEdDSASigner` vectors, PF-067) |
| **Related findings** | PF-023, PF-067, PF-073 |
| **Notes** | The first pairing attempt produced six QR payloads from live refs, and the phone answered "couldn't link new device". The payload carried `eSkeySig = 64 × 0x00`: exactly the right length, so `protocol/auth` accepted it, but not a signature. The reference signs the prekey with the identity key before sending it. This is a concrete divergence found by running rather than reading. **Limits**: the phone's message is generic; that this was *the* cause of the link failure is not proven, only that it was a genuine defect that had to be fixed before any other cause could be ruled out. |

## PF-073: Pairing completes only after pair-device-sign

| Field | Value |
|-------|-------|
| **ID** | PF-073 |
| **Title** | After verifying `pair-success` the client must reply with `iq{type=result, id=<pair-success id>}` containing `<pair-device-sign><device-identity key-index=…>`, carrying the self-signed identity with the account key removed |
| **Layer** | pairing |
| **Source** | reference study of whatsmeow `pair.go` `handlePair` |
| **Observed date** | 2026-11-15 |
| **Confidence** | Probable |
| **Status** | Verified-by-test |
| **Proving test** | `protocol/pairing` (`TestSignDeviceIdentityDropsAccountKey`, `TestSignDeviceIdentityRejectsBadInput`) |
| **Related findings** | PF-016, PF-017 |
| **Notes** | Message is `0x06,0x01 ‖ details ‖ identityPub ‖ accountSignatureKey`, signed with the identity key. The container sent back has `details`, `accountSignature`, and `deviceSignature`, but **not** `accountSignatureKey`, which stays server-side. WhatsCore's probe previously verified `pair-success` and then stopped, so the phone would have shown a device that never finished linking even on a successful scan. An `iq{type=error}` with code `401` `signature-mismatch` or `500` `internal-error` is the reference's way of reporting a bad container. |

## PF-074: Pairing QR refs expire and must be rotated

| Field | Value |
|-------|-------|
| **ID** | PF-074 |
| **Title** | The six refs are not simultaneously valid: the first is offered for 60 s and each following one for 20 s, so showing all six at once guarantees an expired scan |
| **Layer** | pairing |
| **Source** | reference study of whatsmeow `qrchan.go` `emitQRs` |
| **Observed date** | 2026-11-15 |
| **Confidence** | Probable |
| **Status** | Verified-by-test |
| **Proving test** | `cmd/whatscore-probe` (`TestQRValidityWindowMatchesTheReference`, `TestRotationShowsOneCodeAtATime`) |
| **Related findings** | PF-015, PF-069 |
| **Notes** | `timeout := 20 * time.Second; if len(codes) == 6 { timeout = 60 * time.Second }` applies to the first code only. The probe now prints one code at a time, clears the terminal between codes, and keeps answering keepalives throughout — verified live: codes 1 and 2 were each shown for their window with pings answered in between. This alone can explain a scan failure, which is why the previous run could not distinguish expiry from PF-072. |

## PF-075: pair-success verified end to end against the live server

| Field | Value |
|-------|-------|
| **ID** | PF-075 |
| **Title** | A phone scan of a WhatsCore-generated QR produced a real `<iq><pair-success>`; decoding it needed eight single-byte tokens and one dictionary-0 token beyond the `pair-device` set, and the account identity in it verified against the adv secret from our own QR |
| **Layer** | pairing |
| **Source** | direct observation of own session |
| **Observed date** | 2026-11-15 |
| **Confidence** | Confirmed |
| **Status** | Verified-by-test |
| **Proving test** | `protocol/pairing` (`TestPairSuccessToConfirmation`), `protocol/binary` recorded-frame decode |
| **Related findings** | PF-016, PF-017, PF-069, PF-073, PF-074 |
| **Notes** | The 731-byte stanza decoded to `<iq from="s.whatsapp.net" id type="set" xmlns="md"><pair-success><jurisdiction cc="62" iso="ID"/><encryption-metadata algorithm="aes-256-gcm" version="1"><encrypted_key/><nonce/><encrypted_data/><auth_tag/></encryption-metadata><client-props/><platform name="iphone"/><device-identity/><device jid lid/></pair-success></iq>`. Two independent decoders — this project's and the reference's — produced the same tree, attribute by attribute and byte for byte; the `pair-device-sign` path then produced a confirming container. **The account-identity HMAC verified with the adv secret of the QR that was scanned, and the account signature verified with its identity key.** That is the strongest statement this project can make about pairing: the server accepted our device and signed it for our keys. It is *not* a claim that a session works — the `pair-success` arrived, the probe could not read it at the time, and no message has ever been sent. |

## PF-076: A verified pair-success that is never confirmed becomes a stream error

| Field | Value |
|-------|-------|
| **ID** | PF-076 |
| **Title** | After `pair-success` the server waits for the `pair-device-sign` confirmation; a client that does not send it is sent `<stream:error>` and then `xmlstreamend` |
| **Layer** | pairing |
| **Source** | direct observation of own session |
| **Observed date** | 2026-11-15 |
| **Confidence** | Confirmed |
| **Status** | Verified-by-test |
| **Proving test** | `protocol/pairing` (`TestSignDeviceIdentityDropsAccountKey`) and the recorded frames |
| **Related findings** | PF-073, PF-075 |
| **Notes** | Two frames followed the unread `pair-success` in the same run: `<stream:error><ping id="1262735447"/></stream:error>` — echoing the pair-success iq id — and then an empty `<xmlstreamend/>`. It also explains why the phone showed no device afterwards. |

## A cosmetic divergence that is deliberately kept

`binary` renders a userless JID as `@s.whatsapp.net`; the reference renders the
same bytes as `s.whatsapp.net`. The wire form is identical and both are correct
decodes, but the strings differ.

This package keeps the empty user on purpose. The pairing acknowledgement echoes
the server's `from` attribute, and the encoder writes a JID pair back as a JID
pair. If the decoder returned the bare server name, the encoder would emit it as
a plain string instead — same meaning, different bytes. The acknowledgement has
been accepted with the current behaviour, so it stays. It is recorded here
because a future reader comparing decodes will see the difference and should not
"fix" it.
