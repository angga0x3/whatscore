# Pairing findings

Device-pairing payloads of the multi-device flow. Extracted from read-only
reference study of whatsmeow `pair.go` on 2026-11-15; no live pairing run is
recorded yet, so findings stay **Probable**.

## PF-015: QR payload format

| Field | Value |
|-------|-------|
| **ID** | PF-015 |
| **Title** | A pairing QR encodes `https://wa.me/settings/linked_devices#<ref>,<noisePub>,<identityPub>,<advSecret>,<clientType>` with base64 (standard, padded) 32-byte keys |
| **Layer** | pairing |
| **Source** | inferred — reference study |
| **Observed date** | 2026-11-15 |
| **Confidence** | Probable |
| **Status** | Verified-by-test |
| **Proving test** | `protocol/pairing` (golden QR, round-trip) |
| **Related findings** | PF-004 (Noise static key), PF-016 (planned) |
| **Notes** | whatsmeow `makeQRData(ref, clientType)`: `fmt.Sprintf("https://wa.me/settings/linked_devices#%s,%s,%s,%s,%s", ref, base64(noisePub), base64(identityPub), base64(advSecret), clientType)`. `ref` is the raw content of a `<ref>` child in the server's `<pair-device>` node (typically ASCII). `clientType` is an opaque enum value; it may be empty when unknown. QR rendering is a caller concern. |

## PF-016: pair-device and pair-success stanzas

| Field | Value |
|-------|-------|
| **ID** | PF-016 |
| **Title** | The server sends `<iq><pair-device><ref>…</ref></pair-device></iq>`; the client acks with an iq result, and pairing completes with `<iq><pair-success>` carrying `device@jid`, `device@lid`, `biz@name`, `platform@name`, `client-props` bytes, and `device-identity` bytes |
| **Layer** | pairing |
| **Source** | inferred — reference study |
| **Observed date** | 2026-11-15 |
| **Confidence** | Probable |
| **Status** | Verified-by-test |
| **Proving test** | `protocol/pairing` (stanza table, binary round-trip) |
| **Related findings** | PF-015 |
| **Notes** | whatsmeow `handlePairDevice` acks with `iq{to: from, id, type: result}` and skips non-`ref` children; `handlePairSuccess` reads the iq `id`, the `pair-success` child, and its `device` (`jid`, `lid`), `biz` (`name`), `platform` (`name`), `client-props`, and `device-identity` children. `device-identity` is an `ADVSignedDeviceIdentityHMAC` protobuf: HMAC-SHA256 over `details` with the adv secret, then account/device XEdDSA signatures. WhatsCore currently returns those bytes opaque; verification and credential provisioning are pending. |

## PF-017: Device-identity authentication

| Field | Value |
|-------|-------|
| **ID** | PF-017 |
| **Title** | `pair-success.device-identity` is an `ADVSignedDeviceIdentityHMAC`: HMAC-SHA256 over `details` with the adv secret, then an account XEdDSA signature over `prefix ‖ details ‖ identityPub` |
| **Layer** | pairing |
| **Source** | inferred — reference study |
| **Observed date** | 2026-11-15 |
| **Confidence** | Probable |
| **Status** | Verified-by-test |
| **Proving test** | `protocol/pairing` (identity table: E2EE, hosted, 12 negatives) |
| **Related findings** | PF-016 |
| **Notes** | Proto field numbers: `ADVSignedDeviceIdentityHMAC{details=1, HMAC=2, accountType=3}`, `ADVSignedDeviceIdentity{details=1, accountSignatureKey=2, accountSignature=3, deviceSignature=4}`, `ADVDeviceIdentity{rawID=1, timestamp=2, keyIndex=3, accountType=4, deviceType=5}`. HMAC message is `details`, or `0x06 0x05 ‖ details` for `HOSTED`; account signature prefix is `0x06 0x00` (E2EE) or `0x06 0x05` (HOSTED), with the 32-byte `accountSignatureKey` and 64-byte signature. The device signature (prefix `0x06 0x01`, over `details ‖ identityPub ‖ accountSignatureKey`) is generated by us and is not verified by the server; generation and credential provisioning are pending. |

## PF-069: The live pairing exchange decodes with twelve tokens

| Field | Value |
|-------|-------|
| **ID** | PF-069 |
| **Title** | The `pair-device` stanza and the subsequent keepalive decode exactly with ten single-byte tokens and two dictionary-1 tokens; the acknowledge is accepted and the server keeps the socket open by pinging `<iq xmlns="urn:xmpp:ping" type="get">` roughly every 30 s |
| **Layer** | pairing |
| **Source** | direct observation of own session |
| **Observed date** | 2026-11-15 |
| **Confidence** | Confirmed |
| **Status** | Verified-by-test |
| **Proving test** | `deployments/tokendict` live run: pair-device decoded to 6 refs, ack sent, two pings decoded and answered |
| **Related findings** | PF-016, PF-068, PF-070 |
| **Notes** | Full decode: `<iq from="@s.whatsapp.net" type="set" id xmlns="md"><pair-device><ref>×6</ref></pair-device></iq>`, then `<iq from type="get" t xmlns="urn:xmpp:ping">`. Answering the ping with an `iq result` carrying the same id keeps the connection alive; ignoring it produces the 1006 close that earlier runs read as "the acknowledgement was rejected". A first mapping placed `t` at index 22 and `xmlns` at 26 and left 41 unknown; the keepalive decode contradicted it, and the corrected ordering (`22=xmlns`, `26=t`, `41=get`, `43=urn:xmpp:ping`) now matches an independent byte walk. That correction is the reason this finding is worth trusting: the wrong table decoded without error. |

## PF-070: Keepalive, not rejection

| Field | Value |
|-------|-------|
| **ID** | PF-070 |
| **Title** | An unpaired session that acknowledges `pair-device` is kept alive by `<iq xmlns="urn:xmpp:ping" type="get" t>`; a client that does not answer is disconnected about 30 s later with a 1006 close |
| **Layer** | transport |
| **Source** | direct observation of own session |
| **Observed date** | 2026-11-15 |
| **Confidence** | Confirmed |
| **Status** | Verified-by-test |
| **Proving test** | `deployments/tokendict` live run: two pings answered, socket stayed open across both |
| **Related findings** | PF-069 |
| **Notes** | Pings arrived with `t` values 31 s apart, consistent with the reference client's keepalive interval. Answering requires an `iq` with `type="result"`, `to="s.whatsapp.net"`, and the ping's `id`; the amount of the reply did not matter to the server within the window observed. This also means a client that stops reading looks like a rejected pair to any observer who only watches for closes. |

Status: the pairing stanza, the acknowledge, and the keepalive round-trip

arrives after a phone scans a QR composed from these refs.
