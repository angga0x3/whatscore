# v0.0.1 — protocol foundation preview

Released 2026-11-15. This is the first tag, and it is deliberately narrow: the
protocol foundation, with an honest statement of what has been proven against
the real service and what has only been proven against a fake server.

## What this release is

An independent WhatsApp Web protocol implementation in pure Go, with no CGo and
no dependency on another client's protocol code. It ships a protocol engine, an
SDK facade, and a self-hosted REST server; the REST surface manages sessions,
messages, media, webhooks, and SSE streams.

## Proven against the live service

Reproduce with `go run ./cmd/whatscore-probe -payload`:

| Capability | Evidence |
|------------|----------|
| WebSocket dial + headers | 4/4 runs, 2026-11-15 |
| Intro header + frame reassembly | same runs |
| Noise handshake, msg1→msg3 | same runs |
| Server certificate chain against the pinned root | same runs |
| Registration `ClientPayload` accepted | server answers 679 bytes |
| `pair-device` stanza decoded (6 refs) | 9-token partial table |
| iq result accepted by the server | it answers with a 20-byte iq |

The `pair-device` decode is the first complete request/response round trip this
project has made with WhatsApp.

## Not proven

Everything else, and the capabilities below are stated as untested rather than
working:

- **Pairing completion.** The server's post-ack reply uses three token indices
  that never appear in a stanza we can read without them. They are left empty
  in `deployments/tokendict/pairing-minimal.json` and documented as unverified.
  A differential test failed to distinguish them, so no guess was kept.
- **Binary node encoding against real traffic.** Only the pairing stanza has been
  decoded. The full token table is operator data (ADR 0002) and does not ship.
- **Message send/receive, media transfer, app-state sync.** Implemented and
  covered by vector and fake-server tests; never exercised against a live
  account.

`docs/architecture/compatibility.md` is the authoritative matrix.

## Decided, not implemented

- **Token table** — ADR 0002: operator-supplied input, validated at startup,
  never committed. `cmd/tokendict` enforces provenance and shape.
- **XEdDSA signing** — implemented in `internal/xeddsa` and validated against
  known-answer vectors produced by `go.mau.fi/libsignal`, not by our own code.
  It has not been exercised in a live pairing.

## Performance

Measured, with the reproduce commands in `docs/architecture/performance.md`:
binary encode 1.25 µs/7 allocs, Signal encrypt 3.1 µs/19 allocs, media encrypt
518 MB/s streaming, rate limiter 144 ns with zero allocations. No head-to-head
comparison against other implementations is claimed, because that would need a
live account and the same operation on both sides.

## Known limits

- Sessions are held in memory; restarting the process clears them.
- `WHATSAPP_SESSION_LIMIT` is parsed but not enforced.
- The REST message route queues and records; it does not deliver.

## What would make the next release

A token table that makes the post-ack reply readable, or a longer observation
that separates the three unknown indices. That is the single blocker between
this preview and a pairing-capable release.
